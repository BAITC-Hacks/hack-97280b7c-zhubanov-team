# Четырёхчасовой спринт: прогноз выработки ВЭС

**Старт:** 23 сентября 2026, 13:40 GMT+5. Если команда начинает позже, сдвиньте все контрольные точки на одинаковое число минут. **Дедлайн рабочего MVP:** 17:40 GMT+5. Один человек — фронтенд и дизайн; двое — бэкенд/данные и модель. Общий репозиторий и правила: `AGENTS.md`, интерфейс: `docs/api-contract.md`.

## Решение по обучению

**Да, модель обучаем.** Для каждой турбины строим собственную базовую зависимость нормализованной мощности от скорости ветра и температуры на исторических данных до даты расчёта. Быстрый надёжный вариант — эмпирическая кривая мощности: сгруппировать наблюдения по скорости ветра (например, шаг 0,5 м/с), получить медианную мощность, сгладить пустые интервалы и ограничить выход [0,1]. Это обучаемая модель, но без дорогого перебора гиперпараметров. Если остаётся время и установлен `scikit-learn`, сравнить с `HistGradientBoostingRegressor` на той же временной валидации и взять лучший подтверждённый вариант.

Нельзя обучить модель на фактической февральской выработке: её нет в двух CSV. Для выпуска 31 января использовать только наблюдения, которые были доступны к моменту выпуска, а не автоматически весь файл до 31 января 23:50. Погоду для будущих часов брать из `backend/weather.py` — архивного прогноза, доступного на момент расчёта. Историческая фактическая скорость ветра допустима для построения кривой мощности, но **не** как будущая погода в оценке качества прогноза.

Честная проверка: выделить несколько дат в январе до 31-го; для каждой обучить модель только на более ранних измерениях, получить архивный прогноз погоды на 24/48 часов и сравнить прогнозируемую мощность с фактической мощностью соответствующих часов. Сначала зафиксировать допущение о часовом поясе CSV; если его не удастся подтвердить, показать MAE как условный результат при указанном смещении и отдельно проверить чувствительность к сдвигу времени. Не называть метрику на измеренной будущей скорости ветра реальной точностью погодного прогноза. Февраль показать как прогнозный период без MAE до появления фактических данных.

## Разделение работы и границы файлов

| Участник | Ветка | Ответственность | Не блокирует остальных |
|---|---|---|---|
| 1 — фронтенд/дизайн | `feat/frontend` | `frontend/`: экран с двумя графиками, выбор времени выпуска и горизонта, погодный источник и время запуска модели, кнопка перерасчёта, состояния загрузки/ошибки. Начать с JSON из `docs/api-contract.md`. | Не менять `backend/` и `forecast/`. |
| 2 — бэкенд/интегратор | `feat/backend-api` | `backend/`: загрузка двух CSV, проверка дат/пропусков, часовая агрегация, API `run`/`rolling`, вызов готового погодного клиента и модели. | 3 — модель/оценка | `feat/forecast-core` | `forecast/`: обучение двух моделей, предсказание [0,1], воспроизводимая временная валидация, метрики, диагностическое объяснение входов/изменения прогноза. | Чистая функция `predict(turbine_id, weather_hourly, training_cutoff)` для подключения к API. |

Сейчас `main` уже содержит проверенный `backend/weather.py` для обеих турбин. Участник 2 использует его, а не пишет второй погодный клиент.

## Часы и обязательные публикации

Каждый участник **в конце каждого часа делает коммит и `git push` в свою ветку**, даже если часть задачи ещё не закончена. Коммит должен сохранять запускаемое состояние своей части или явно описывать ограничение. После push — короткое сообщение команде: ссылка на коммит/PR, что работает, что мешает, что будет в следующий час. Интегратор обновляет PR и проверяет три ветки. Не складывать незавершённую работу на `main`; не делать force-push.

## Минимальный сценарий для судей

1. Выбрать выпуск **31 января 2026, 12:00 UTC**, горизонт **48 часов**.
2. Показать 48 почасовых точек по каждой из двух турбин, источник и UTC-время архивного погодного запуска, время окончания обучающих данных.
3. Показать перерасчёт для **1 февраля 2026, 12:00 UTC** и объяснить, что изменилось в погодном входе/прогнозе.
4. Показать последовательность выпусков до 28 февраля и честно назвать январскую валидацию, отсутствие февральских фактических значений, неопределённый часовой пояс и отсутствие мощности турбин в MW.

## Если время заканчивается

Приоритет: **один настоящий 48-часовой прогноз двух турбин с архивной погодой → повторный выпуск → январская валидация → полный февральский цикл → визуальная полировка**. Если внешний погодный API недоступен, используйте ранее полученный кэш архивного запуска с точной меткой источника/времени; не подменяйте его фактической погодой. Если ML-библиотека не установлена, оставьте обученную эмпирическую кривую мощности. Если февральских фактических значений нет, не выдумывайте метрику за февраль.
